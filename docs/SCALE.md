# Scale & Efficiency — measured results

The chosen stretch goal. This documents how the pipeline behaves with a
meaningfully large simulated fleet, with real numbers (measured on the dev
machine, PostgreSQL 17, 2026-07-27).

## Test fleet
- **2,000 devices**, generated by `py simulator/simulator.py --reset --fleet-size 2000`.
- **50,000 readings** after a short burst; ~700 active alarms.

## The efficiency principle
As the fleet grows, **response size and query cost stay flat** — the UI never
fetches data proportional to the whole fleet.

| What | Approach | Measured |
|---|---|---|
| Whole-fleet tallies | one aggregate over `device_status` (`GET /api/fleet/summary`) | **~5 ms**, ships ~90 bytes regardless of fleet size |
| Fleet grid | bounded worst-first page (`GET /api/fleet?limit=200`) | **~17 ms**, **47 KB** for 200 rows |
| — vs. shipping the whole fleet | `?limit=5000` (2,000 rows) | 467 KB — **~10× larger** |
| Drill-down history | incremental `?since=` cursor, not full refetch | returns only new rows per poll |

At 10,000 devices the bounded page stays ~47 KB while an unbounded fetch would be
~2.3 MB per poll. The bounded design is what keeps the frontend from overloading
the backend as the fleet grows.

## Write path (simulator)
- **2,000 readings per tick in ~100–200 ms** — one multi-row `COPY` for readings
  plus a batched `ON CONFLICT` upsert for `device_status`, not per-device
  round-trips. At a 2 s cadence that is a ~5–10% duty cycle, leaving ample headroom.

## Indexes do the work (no sequential scans)
`EXPLAIN ANALYZE` over 50,000 readings:

- **Drill-down delta** — `readings WHERE device_id=? AND ts > ?`
  → *Index Scan Backward using `idx_readings_device_ts`*, **~0.2 ms**.
- **Active-alerts feed** — `alarms WHERE cleared_at IS NULL`
  → *Index Scan using the partial index `idx_alarms_active`*, **~0.1 ms**.

## Frontend at 2,000 devices
- Grid keeps **only 200 cards in the DOM** (the worst-first page), not 2,000.
- `content-visibility: auto` skips layout/paint for off-screen cards.
- Status tallies come from the summary endpoint (one aggregate), not by counting
  rows in the browser.
- Filtering, worst-first sorting, and pagination are all **server-side**, so the
  payload is bounded no matter how large the fleet gets.
- Search is debounced (300 ms) to avoid a request per keystroke.
- Polling **pauses when the tab/pane is hidden** (no wasted cycles).

## How to reproduce
```bash
py simulator/simulator.py --reset --fleet-size 2000 --ticks 25 --interval 0.01   # write burst + timings
# then, with the API running:
curl -s "http://127.0.0.1:8000/api/fleet/summary"
curl -s "http://127.0.0.1:8000/api/fleet?limit=200" -o /dev/null -w "%{size_download} bytes\n"
```
